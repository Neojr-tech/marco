# MAPA DE REFERÊNCIAS TÉCNICAS PARA IMPLEMENTAÇÃO — CHATBOT NAMORADO VIRTUAL

**Projeto:** Chatbot Namorado Virtual
**Função deste documento:** Referência técnica e registro de soluções encontradas em projetos externos
**Status:** Documento auxiliar — não substitui nem altera as Etapas 1, 2, 3 e 4
**Objetivo:** Registrar materiais técnicos relevantes encontrados durante a pesquisa para futura análise, comparação e possível incorporação de soluções ao projeto.

---

## 1. COMO ESTE DOCUMENTO DEVE SER UTILIZADO

Este documento não define a arquitetura do Chatbot Namorado Virtual.

As decisões oficiais continuam sendo aquelas estabelecidas nas **Etapas 1, 2, 3 e 4** e no **Documento de Integração das Etapas 1–4**.

Este material funciona como um **mapa de referências**.

Sempre que for necessário resolver uma questão técnica do projeto, consultar primeiro este documento para verificar se já encontramos uma solução semelhante em algum projeto externo.

Nenhum projeto relacionado abaixo deve ser incorporado automaticamente.

A regra é:

> **Encontrar → estudar → comparar → validar → decidir → somente então utilizar.**

Um projeto não deve ser descartado simplesmente porque não corresponde exatamente ao nosso produto. Uma solução parcial pode fornecer uma informação útil para uma parte específica da nossa estrutura.

# 3. REFERÊNCIA PRIORITÁRIA — OPEN-LLM-VTUBER

**Projeto:** Open-LLM-VTuber
**Fonte:** GitHub
**Categoria:** Avatar conversacional / LLM / voz / execução local / integração de componentes

### Por que foi considerado relevante

O projeto apresenta uma arquitetura próxima de vários elementos que pretendemos construir.

Entre os pontos de interesse estão:

* conversação com personagem;
* interação por voz;
* avatar;
* Live2D;
* memória/histórico;
* utilização de diferentes LLMs;
* componentes de reconhecimento de voz;
* síntese de voz;
* possibilidade de execução local;
* possibilidade de utilização de serviços externos;
* arquitetura modular.

### Relação com nosso projeto

Pode servir como referência principalmente para:

**`ai-gateway`**

* separação entre o sistema principal e o provedor de IA;
* possibilidade de trocar componentes/modelos.

**Voz**

* ASR;
* TTS;
* fluxo de entrada e saída de voz.

**Avatar**

* integração entre resposta da IA e representação visual.

**Arquitetura híbrida**

* combinação de processamento local com serviços externos.

### O que devemos estudar posteriormente

* como os componentes são separados;
* como o LLM é conectado ao restante do sistema;
* como memória/histórico é tratado;
* como voz entra e sai do fluxo;
* como o avatar recebe os eventos da conversa;
* quais componentes podem ser reproduzidos conceitualmente em nossa arquitetura.

### Atenção

Os assets e modelos utilizados pelo projeto não devem ser considerados automaticamente livres para utilização comercial.

A licença do código e as licenças específicas de modelos, personagens e assets devem ser verificadas individualmente.

# 7. LICENÇAS E DIREITOS DE USO

A existência de um projeto no GitHub não significa automaticamente que todos os seus componentes possam ser utilizados comercialmente.

Devem ser diferenciados:

1. código-fonte;
2. modelos de IA;
3. pesos dos modelos;
4. personagens;
5. imagens;
6. vozes;
7. músicas;
8. animações;
9. datasets;
10. outros assets.

Cada componente deve ter sua própria licença ou condição de uso verificada.

### Exemplo importante

Materiais relacionados ao Live2D podem possuir condições específicas mesmo quando o código de um projeto possui uma licença permissiva.

Portanto:

> **Código aberto ≠ todos os assets livres para uso comercial.**

Esta verificação deverá ser feita antes de qualquer utilização efetiva no produto.

# 11. PRÓXIMA FASE DA PESQUISA

A pesquisa não deve continuar simplesmente acumulando nomes de projetos.

O próximo passo é transformar cada referência em **soluções técnicas identificadas**.

Para cada projeto, analisar:

1. O que ele resolve?
2. Como resolve?
3. Qual componente da nossa arquitetura corresponde a essa solução?
4. A solução é compatível com nossa arquitetura?
5. Podemos reproduzir o conceito?
6. Existe código que possa ser aproveitado legalmente?
7. Existe alguma limitação?
8. Existe uma solução melhor em outro projeto?
9. Essa solução resolve algum dos pontos que deixamos "A DEFINIR"?
10. Deve ser candidata a implementação, apenas referência ou descartada após análise?

# 12. REGRA PARA NOVOS MATERIAIS

Sempre que novos projetos forem encontrados, eles devem ser acrescentados a este documento ou a uma versão posterior deste mapa, mantendo o mesmo padrão.

Não criar uma nova etapa da arquitetura simplesmente porque um novo projeto foi encontrado.

O material externo serve como **fonte de soluções**, não como autoridade sobre o projeto.

A arquitetura do Chatbot Namorado Virtual continua sendo a referência principal.

---

# 13. PRINCÍPIO CENTRAL

O objetivo desta pesquisa não é encontrar um projeto para copiar.

É encontrar **soluções comprovadas para problemas que teremos que resolver**.

A estratégia é:

```text
Nossa arquitetura
      ↓
Problema técnico
      ↓
Pesquisar projetos que já resolveram algo semelhante
      ↓
Encontrar soluções
      ↓
Comparar soluções
      ↓
Validar compatibilidade
      ↓
Escolher a melhor abordagem
      ↓
Implementar na nossa própria arquitetura
```

O resultado final deve ser um aplicativo próprio, com arquitetura coerente, utilizando quando apropriado ideias, técnicas, componentes e referências encontradas em projetos existentes.
