Show, com base e nisso monto uma proposta. Já que vai ser web + celular, o mais prático pra você (que é leigo) é usar **uma tecnologia só que gera os dois ao mesmo tempo**, em vez de duas equipes/códigos separados. Isso reduz muito a complexidade de manutenção.

**Stack recomendada:**
- **Flutter** → um único código gera app Android, iOS e também versão web. É a opção mais simples de manter sozinho.
- **Backend** em Node.js (ou Python) → cuida da conversa com a IA, memória do usuário, login, pagamentos.
- **Banco de dados** PostgreSQL → guarda usuários, histórico de conversas, assinaturas.
- **IA de conversação** via API (ex: OpenAI, Anthropic, ou outro provedor) → você não precisa treinar modelo próprio nem rodar nada pesado localmente pra isso.

**Estrutura de pastas proposta:**

```
namorado-virtual/
├── app/                    → código do Flutter (tela, chat, perfil, assinatura)
│   ├── lib/
│   │   ├── screens/        → telas (login, chat, configurações, planos)
│   │   ├── widgets/        → componentes reutilizáveis (bolha de chat, avatar)
│   │   ├── services/       → conexão com o backend
│   │   └── models/         → estrutura dos dados (usuário, mensagem)
│   └── assets/              → imagens, ícones, avatar do personagem
│
├── backend/                → servidor

│   └── database/            → scripts do banco de dados

```

```
Abertura do app
      ↓
Onboarding (boas-vindas + verificação de idade 18+)
      ↓
Cadastro / Login
      ↓
Criação do personagem (nome, aparência, personalidade)
      ↓
Tela de Chat (tela principal)
      ↓
Explorar / Configurações / Perfil
```

## Telas detalhadas

**1. Onboarding**
- Tela de boas-vindas (apresenta o app rapidamente)
- Verificação de idade (18+)
- Aceite de termos de uso e política de privacidade

**2. Cadastro / Login**
- Login por e-mail, ou login social (Google/Apple)
- Recuperação de senha

**3. Criação do personagem**
- Escolha de nome
- Escolha de aparência (avatar/estilo visual)
- Escolha de personalidade/traços (ex: carinhoso, engraçado, atencioso)
- Isso pode ser simples no início e evoluir depois

**4. Tela de Chat (tela principal, onde o usuário passa mais tempo)**
- Histórico de mensagens
- Campo de digitação + envio de mensagem
- Indicador de "digitando..."
- Acesso rápido ao perfil do personagem (avatar clicável no topo)

**5. Perfil do personagem**
- Foto/avatar
- Personalidade (editável)
- Nível de relacionamento/progresso (se você quiser gamificar)

**6. Configurações**
- Conta (dados do usuário, senha)
- Notificações
- Plano/assinatura (só quando você decidir ativar isso)
- Suporte/ajuda
- Sair da conta

**7. Menu de navegação**


## 0. Premissa geral

A stack proposta (Flutter + Node.js + PostgreSQL + APIs de IA externas) é adequada para este projeto e será mantida como ponto de partida, com um ajuste de enfoque: a arquitetura não deve ser organizada em torno de "um chatbot", mas em torno de **entidades configuráveis** (personagens, avatares, conversas, memórias) que o chatbot consome. Isso muda a lógica interna das pastas propostas originalmente, mesmo mantendo os nomes de alto nível (`app/`, `backend/`, `docs/`).

Nenhuma decisão de modelo de IA, preço ou design visual é tomada nesta etapa — apenas onde essas decisões vão "encaixar" futuramente.

## 2 e 3. Explicação e responsabilidade de cada pasta

### `app/lib/screens/`
**Função:** cada subpasta representa um fluxo completo de tela (não um componente isolado).
**Entra:** os arquivos de tela em si (ex: `chat_screen.dart`) e, quando necessário, sub-componentes que só fazem sentido *dentro* daquele fluxo específico.
**Não entra:** lógica de chamada de API (isso vai para `services/`) nem componentes reutilizáveis em outras telas (isso vai para `widgets/`).
**Relação:** consome `widgets/`, `services/` e `models/`; não é consumida por ninguém (é a camada mais "de fora").
**Motivo:** ao crescer o número de personagens/fluxos, cada tela permanece isolada e fácil de localizar.

### `app/lib/widgets/`
**Função:** peças visuais reaproveitáveis em mais de uma tela.
**Entra:** bolha de chat, avatar circular, cartão de personagem, botões padronizados.
**Não entra:** nada que dependa de uma tela específica só ela usa — isso deveria estar dentro da própria pasta da tela.
**Relação:** usada por `screens/`; não deve depender de `screens/`.
**Motivo:** evita duplicar visual quando novos personagens/telas forem adicionados.

### `app/lib/services/`
**Função:** ponte entre o app e o backend.
**Entra:** funções que fazem requisições HTTP/WebSocket, tratam resposta, tratam erro de rede.
**Não entra:** lógica de IA, regras de negócio (isso é responsabilidade do backend).
**Relação:** chamada por `screens/`; consome `models/` para tipar os dados.
**Motivo:** se amanhã trocar a forma de comunicação (ex: REST → WebSocket para chat em tempo real), só essa camada muda.

### `app/lib/models/`
**Função:** representar os dados que circulam no app (o "formato" de um personagem, uma mensagem, um usuário).
**Entra:** classes de dados e conversão de/para JSON.
**Não entra:** lógica de tela ou chamada de rede.
**Relação:** usada por `services/`, `widgets/` e `screens/`.

### `app/lib/platform/`
**Função:** isolar as poucas diferenças reais entre mobile e web/desktop (ex: notificações push só existem em mobile).
**Motivo:** mantém o resto do código 100% compartilhado; só aqui existe ramificação por plataforma (ver seção 11).

---

### `backend/src/routes/`
**Função:** definir *quais* endpoints existem e para qual serviço encaminhar a chamada. Deve ser "fino" — sem regra de negócio.
**Não entra:** lógica de IA, cálculo de memória, validação complexa.
**Relação:** chama `services/`; é o ponto de entrada do backend.

### `backend/src/services/`
**Função:** onde a lógica de negócio realmente acontece.
**Subpastas e responsabilidade:**
- `auth/`: cadastro, login, sessão.
- `chat/`: orquestra o envio/recebimento de mensagens, decide se é conversa individual ou em grupo, monta o contexto que será enviado à IA.
- `character/`: CRUD de personagens, personas e avatares; regras de qual persona pode usar qual avatar.
- `memory/`: lê e grava as diferentes camadas de memória (seção 7), decide o que entra no contexto de uma conversa.
- `ai-gateway/`: única camada que efetivamente conversa com provedores de IA externos (seção 6).
**Motivo:** se uma regra de negócio muda, o ponto de alteração é sempre aqui — nunca em `routes/` nem no app.

### `backend/src/models/`
**Função:** representar as tabelas do banco via ORM.
**Não entra:** lógica de negócio (fica em `services/`).

### `backend/src/config/`
**Função:** variáveis de ambiente, chaves de API, parâmetros que mudam entre desenvolvimento e produção.
**Motivo:** nenhuma chave sensível deve estar espalhada pelo código.

### `backend/database/`
**Função:** controle de versão do schema (migrations) e dados de exemplo (seeds).

### `docs/`
**Função:** cada arquivo é a **fonte oficial** de um assunto — não deve haver dois documentos falando da mesma coisa. `decisions-log.md` registra o que foi **Definido / Em teste / Descartado**, evitando redecidir a mesma coisa depois.

## 4 e 5. Personagens: separação entre avatar e persona

O sistema não deve tratar "personagem" como uma pasta ou arquivo fixo (ex: `marco/`). Em vez disso, existem **duas entidades separadas no banco de dados**, ligadas entre si:

```
Avatar                         Persona (Personagem)
─────────────────              ──────────────────────
- aparência/imagem             - nome
- (futuro: voz, vídeo)         - personalidade
- id                            - forma de falar
                                 - história/backstory
                                 - regras de comportamento
                                 - avatar_id (referência)
                                 - relacionamento com o usuário
```

Uma **Persona** referencia um **Avatar**, mas não é o mesmo registro. Isso permite:
- o mesmo avatar visual ser reaproveitado por mais de uma persona (ex: mesmo rosto, personalidades diferentes em contextos diferentes);
- trocar a personalidade de um personagem sem mexer na parte visual, e vice-versa;
- no futuro, suportar personagens masculinos, femininos, casais, grupos — cada um é apenas um novo registro de Persona, não uma nova pasta ou novo código.

Essa separação vive em `backend/src/services/character/` e nas tabelas `character.model.js` / `avatar.model.js`.

---

## 6. Sistema de IA (camada de abstração)

Toda comunicação com modelos de IA passa exclusivamente por `backend/src/services/ai-gateway/`. Nenhuma outra parte do sistema (nem o app, nem as rotas, nem `chat/`) fala diretamente com um provedor de IA.

Estrutura interna sugerida:

```
ai-gateway/
├── conversation/        # interface única para "gerar resposta de texto"
├── vision/               # interface única para "analisar imagem"
├── image-generation/     # interface única para "gerar imagem"
├── video-generation/     # interface única para "gerar vídeo"
├── voice/                # interface única para "texto→voz / voz→texto"
└── index.js               # ponto único de entrada, decide qual provedor usar por função
```

Cada subpasta define **uma interface fixa** (ex: `gerarResposta(contexto) → texto`), e por trás dela pode existir qualquer provedor específico, plugado ou trocado sem que `chat/`, `character/` ou o app percebam diferença. Essa é a camada que garante o requisito "trocar modelos depois sem reconstruir o app".

---

## 7. Memória e contexto

Camadas separadas, todas geridas por `backend/src/services/memory/`:

| Camada | O que guarda | Escopo |
|---|---|---|
| Histórico de conversa | mensagens trocadas | por conversa |
| Contexto atual | recorte recente enviado à IA a cada chamada | por conversa, temporário |
| Memória do personagem | traços fixos daquela persona (não muda por usuário) | por persona |
| Memória do usuário | preferências, fatos que o usuário compartilhou | por usuário |
| Relacionamento usuário↔personagem | histórico específico daquele vínculo (nível, marcos, tom) | por par usuário+persona |
| Memória de grupo *(futuro)* | o que aconteceu numa conversa com múltiplos personagens | por conversa em grupo |

Tecnicamente, isso se traduz em tabelas separadas no banco (não um único "campo memória"), permitindo consultar só o necessário para montar o contexto de cada chamada de IA — evitando enviar memória irrelevante e mantendo custo/latência controlados.

---

## 8. Conversas individuais e em grupo

`backend/src/services/chat/` é responsável por decidir o tipo de conversa e montar o contexto adequado:

- **Individual:** contexto = histórico da conversa + memória daquela persona + memória do usuário + relacionamento.
- **Grupo:** o serviço de chat, a cada mensagem, monta o contexto **por personagem** (cada persona "vê" a conversa toda, mas responde com sua própria personalidade), e decide a ordem/quem responde. Isso exige que `conversation.model.js` suporte múltiplos participantes (não um campo fixo "personagem_id", mas uma tabela de participantes).

Nada disso é implementado agora — apenas a divisão em `chat/` (orquestração) e `memory/` (dados) já comporta essa evolução sem redesenho.

---

## 9. Resumo de responsabilidades do backend

| Responsabilidade | Onde fica |
|---|---|
| Autenticação | `services/auth/` |
| Usuários | `services/` (auth) + `models/user.model.js` |
| Personagens/avatares | `services/character/` |
| Conversas (individual/grupo) | `services/chat/` |
| Memória | `services/memory/` |
| Comunicação com IA | `services/ai-gateway/` |
| Pagamentos *(futuro)* | novo módulo `services/billing/`, isolado do resto |
| Geração de mídia | dentro de `ai-gateway/image-generation` e `video-generation` |
| Armazenamento de arquivos | novo módulo `services/storage/` quando necessário |
| Configurações do sistema | `config/` |

---

## 10. Frontend (detalhamento)

- `screens/`: um fluxo por pasta, sem lógica de rede.
- `widgets/`: qualquer peça usada em 2+ telas.
- `services/`: só comunicação com backend, nunca lógica de IA.
- `models/`: formato de dados espelhando o que o backend envia.
- `assets/`: estáticos que fazem parte do app em si (ícones, fontes); avatares/imagens **geradas** de personagens não ficam aqui — vêm do backend/storage, pois são dinâmicos.

---

## 11. Web/Desktop e Mobile

**Compartilhado (a grande maioria):** `screens/`, `widgets/`, `services/`, `models/`, `state/` — é justamente a vantagem do Flutter, um único código para as três saídas.

**Específico por plataforma (isolado em `app/lib/platform/`):** notificações push, acesso a câmera/microfone do dispositivo, comportamento de teclado/tela, atalhos de desktop. Tudo isso fica atrás de uma interface comum, e cada plataforma implementa sua versão dentro de `platform/mobile/` ou `platform/web_desktop/`.

---

## 12. Documentação

Um arquivo por assunto, sem redundância:
- `architecture.md` — esta arquitetura, atualizada conforme decisões avançam.
- `characters/` — uma ficha por persona/avatar quando existirem.
- `ai-models.md` — qual modelo está em uso em cada função do `ai-gateway`.
- `memory-system.md`, `database-schema.md`, `api-reference.md` — cada um cobre exclusivamente seu assunto.
- `decisions-log.md` — histórico do tipo "Definido / Em teste / Descartado", para nunca perder o porquê de uma escolha.

---

## 13. Decisões que ainda precisam ser tomadas antes de programar

1. Gerenciador de estado do Flutter (Provider, Riverpod, Bloc etc.).
2. Protocolo de chat em tempo real: HTTP simples (polling) ou WebSocket.
3. Provedor(es) de IA de conversação a plugar no `ai-gateway` (não decidido nesta etapa).
4. Estratégia de armazenamento de mídia gerada (avatares, futura imagem/vídeo) — serviço de storage próprio ou externo.
5. Estrutura exata do banco para "conversa em grupo" (tabela de participantes).
6. Autenticação: e-mail/senha, login social, ou ambos, desde o início.

Essas ficam registradas para decisão na próxima etapa, junto com a transformação desta planta em esqueleto real de pastas e arquivos.

## 4. Estrutura dos personagens (o núcleo do sistema)

Em vez de um arquivo por personagem, existem **três entidades genéricas e reutilizáveis**, cada uma responsável por uma parte:

```
Character (character.model.js)      → entidade "guarda-chuva": liga persona + avatar + dono (usuário/sistema)
   ├── Persona (persona.model.js)   → nome, personalidade, forma de falar, história, regras
   ├── Avatar (avatar.model.js)     → aparência, imagem, futuramente voz/vídeo
   └── (config de IA por personagem, se precisar sobrescrever o padrão)
```

Cada nova "persona" (masculina, feminina, casal como duas personas ligadas à mesma conversa, etc.) é **um novo registro no banco**, nunca um novo arquivo de código. Os arquivos (`character.service.js`, `persona.service.js`, `avatar.service.js`) são genéricos e atendem qualquer quantidade de personagens.

Ficha de referência de cada persona (para uso da equipe, não do sistema em runtime) fica em `docs/characters/`, um arquivo markdown por personagem quando existirem.

## 5. Conversas individuais e em grupo

| Responsabilidade | Arquivo |
|---|---|
| Participantes de uma conversa (1 ou vários personagens) | `participant.model.js` — tabela que liga `conversation` a um ou mais `character` |
| Mensagens | `message.model.js` — cada mensagem referencia quem enviou (usuário ou qual personagem) |
| Contexto enviado à IA | montado dinamicamente por `individual_chat.service.js` ou `group_chat.service.js`, não fica salvo como arquivo fixo |
| Ordem das respostas em grupo | `group_chat.service.js` |
| Identificação de quem falou | campo `sender_id` + `sender_type` (usuário/personagem) em `message.model.js`; exibido no app via `speaker_tag.dart` |
| Relacionamento entre personagens (futuro) | ficaria em `relationship.model.js`, generalizado para também representar personagem↔personagem, não só usuário↔personagem |
| Memória da conversa em grupo | `conversation_memory.service.js` já é genérico o suficiente (não distingue individual/grupo na camada de dados) |

## 7. Prompts

```
prompts/
├── system/            → regras gerais do sistema, válidas para qualquer personagem
├── personas/           → um arquivo-modelo por persona (nome, tom, história) — preenchido quando as personas forem definidas
├── behavior/            → regras de comportamento (o que a persona pode/não pode fazer)
├── relationship/        → como o tom muda conforme o nível de relacionamento
├── memory/              → como a memória é injetada no prompt final
├── group/                → regras de como um personagem deve reagir à fala de outro personagem
└── media/                 → prompts usados pelos gateways de visão/imagem/vídeo/voz
```

Cada tipo de prompt fica isolado para poder ser versionado e ajustado independentemente — por exemplo, mudar a regra de "grupo" não deve exigir mexer no prompt de "sistema".

## 2. Relacionamentos entre User, Character, Persona e Avatar

```
User (1) ───< (N) Character
Persona (1) ───< (N) Character        [uma persona pode ser usada em vários Character,
                                        de usuários diferentes, se owner_type = system]
Avatar (1) ───< (N) Character         [mesma lógica — reaproveitamento]
Avatar (1) ───< (N) Persona           [via default_avatar_id]
```

- `Character` é sempre de 1 usuário (`user_id` obrigatório).
- `Persona` e `Avatar` podem pertencer ao sistema (`owner_type = system`, ex: personagens padrão oferecidos a todos) ou a um usuário específico (`owner_type = user`, ex: personagem customizado do zero).
- A separação persona/avatar permanece mesmo dentro de um `Character`: trocar o avatar de um personagem não cria uma nova persona, e vice-versa.

---

## 3. Conversa, Participantes e Mensagens

```
Conversation (1) ───< (N) Participant >─── (N) Character
Conversation (1) ───< (N) Message
Message.sender_id → User.id  OU  Character.id  (conforme sender_type)
```

- Conversa individual: 1 `Conversation` + 1 `Participant`.
- Conversa em grupo: 1 `Conversation` + N `Participant` (N ≥ 2).
- `Message.sender_type` evita precisar de duas tabelas de mensagem (uma para usuário, outra para personagem) — mantém tudo em uma única tabela, ordenável por `created_at`.

## 4. Camadas de memória — resumo de uso

| Camada | Escopo | Quando é lida |
|---|---|---|
| `Message` (histórico bruto) | por conversa | montagem do contexto recente |
| `ConversationMemory` | por conversa | quando o histórico bruto fica longo demais para caber no contexto de IA |
| `CharacterMemory` | por persona | sempre, para manter consistência da persona entre usuários diferentes |
| `UserMemory` | por usuário | sempre, para personalizar resposta ao usuário específico |
| `Relationship` | por par (user, character) | para ajustar tom conforme o nível do vínculo |
| `GroupMemory` *(futuro)* | por conversa em grupo | quando conversas em grupo forem implementadas |

A junção dessas camadas para montar o "contexto final" enviado à IA é responsabilidade do `ai-gateway` + `chat/` (Etapa 1/2), não do banco.

---

## 5. Relacionamento Usuário ↔ Personagem

Já coberto pela entidade `Relationship` (seção 1.9). Pontos de integridade:
- Um par (`user_id`, `character_id`) deve ser único — não existe mais de um registro de relacionamento para o mesmo par.
- `level` e `milestones` são opcionais porque a decisão de gamificar ou não o vínculo ainda não foi tomada — **a definir**.

---

## 6. Preparação para conversas em grupo

Já modelado via `Participant` (N para N entre `Conversation` e `Character`) e `Message.sender_type/sender_id`. Pontos que ficam **a definir** antes da implementação real:
- Regra de quem responde e em que ordem (lógica de serviço, não de dados).
- Se personagens podem ser adicionados/removidos de uma conversa em grupo já existente (exigiria `left_at` em `Participant` — campo ainda não incluído, marcado como futuro).

---

## 7. Assinatura/monetização — apenas preparação

Coberto pela entidade `Subscription` (seção 1.10). Nenhum plano, preço, gateway de pagamento ou regra de cobrança é definido aqui. A entidade existe só para o schema já prever o relacionamento `User (1) ─── (0..1 ativo) Subscription`.

## 8. Relações entre entidades e regras de integridade

```
User 1 ──< N Character
User 1 ──< N Conversation
User 1 ──< N UserMemory
User 1 ──< 0..1 Subscription (ativa)

Persona 1 ──< N Character
Persona 1 ──< N CharacterMemory
Avatar 1 ──< N Character
Avatar 1 ──< N Persona (via default_avatar_id)

Conversation 1 ──< N Participant
Conversation 1 ──< N Message
Conversation 1 ──< 0..1 ConversationMemory
Conversation 1 ──< 0..1 GroupMemory (futuro, só se type = group)

Character 1 ──< N Participant
Character 1 ──< N Relationship
```

**Regras de integridade principais:**
1. `Character.user_id`, `persona_id`, `avatar_id` são obrigatórios — um Character nunca existe sem os três.
2. `Message.sender_id` deve corresponder a uma entidade válida conforme `sender_type` (validação em nível de aplicação, já que é chave estrangeira "polimórfica" — bancos relacionais não validam isso nativamente).
3. `Participant` não permite duplicar o mesmo `character_id` na mesma `Conversation`.
4. `Relationship` é única por par (`user_id`, `character_id`) quando `subject_type = user_character`.
5. Exclusão de `User`: **a definir** se será exclusão física (apaga tudo em cascata) ou lógica (`status = deleted`, mantendo dados por período de retenção) — decisão pendente de política de privacidade.

```
        ↓
```

A lógica: nada de frontend deve ser construído contra um backend que ainda não existe, e nenhum backend deve ser construído sem o schema de dados que ele vai usar.

## 2. Dependências entre módulos

| Módulo | Depende de | Por quê |
|---|---|---|
| `auth` (backend) | schema `users` | precisa da tabela para gravar/ler conta |

| `criação de personagem` (frontend) | `character/persona/avatar` (backend) pronto | mesma razão |

## 4. Relação entre frontend Flutter e backend Node.js

- Comunicação via **HTTP REST** para a maior parte das ações (login, CRUD de personagem).

## 5–7. Ordem de implementação — banco, backend e frontend

Já detalhadas na sequência da seção 3 (Fases 1, 2–6, e 7–9 respectivamente). Resumo direto:

## 8. Comunicação frontend-backend

```
Tela (screens/) 
   → chama serviço (services/api/*.dart)
      → requisição HTTP para routes/ do backend
         → routes/ encaminha para services/ do backend
            → services/ aplica regra de negócio, consulta models/, chama ai-gateway/ quando necessário
         ← resposta formatada
      ← services/api/ converte JSON em models/ do app
   ← tela atualiza state/ e renderiza
```

Nenhuma tela ou widget do Flutter deve montar a URL da API diretamente — isso fica isolado em `services/api/`, exatamente como definido na Etapa 1.

## 9. Integração de personagens, personas e avatares

1. Backend expõe endpoints separados para `avatar` e `persona` (permitindo, futuramente, montar uma tela que escolhe avatar e persona de forma independente).
2. `character.service.js` é o único ponto que "junta" os três (usuário + persona + avatar) em um `Character` utilizável.
3. No frontend, `character_creation_screen.dart` chama `character_api.dart`, que internamente pode fazer 1 chamada composta (criar tudo de uma vez) ou 3 chamadas (avatar, depois persona, depois character) — **a definir** conforme a experiência de criação que for desenhada depois (não é uma decisão de arquitetura, é de fluxo de produto).

---

## 10. Integração de conversas, mensagens e memória

1. `individual_chat.service.js` recebe a mensagem do usuário, grava em `Message`, monta o contexto (histórico recente + `CharacterMemory` + `UserMemory` + `Relationship`, conforme Etapa 3 seção 4).
2. Contexto montado é enviado ao `ai-gateway/conversation`.
3. Resposta da IA é gravada como novo `Message` (`sender_type = character`).
4. Periodicamente (regra exata **A DEFINIR** — ex: a cada N mensagens, ou por tamanho de contexto), `conversation_memory.service.js` gera/atualiza o resumo em `ConversationMemory`, para não depender só do histórico bruto crescendo indefinidamente.

- `ai_providers.config.js` centraliza qual provedor está ativo em cada gateway — trocar de provedor, ou ativar `vision`/`image-generation`/`video-generation`/`voice` depois, é uma questão de configuração + implementar aquele gateway específico, sem alterar `chat/`, `character/` ou o frontend.
- Escolha do(s) provedor(es) real(is): **A DEFINIR**, fora do escopo desta etapa.

## 2 e 3. Explicação e responsabilidade de cada pasta

### `app/lib/screens/`
**Função:** cada subpasta representa um fluxo completo de tela (não um componente isolado).
**Entra:** os arquivos de tela em si (ex: `chat_screen.dart`) e, quando necessário, sub-componentes que só fazem sentido *dentro* daquele fluxo específico.
**Não entra:** lógica de chamada de API (isso vai para `services/`) nem componentes reutilizáveis em outras telas (isso vai para `widgets/`).
**Relação:** consome `widgets/`, `services/` e `models/`; não é consumida por ninguém (é a camada mais "de fora").
**Motivo:** ao crescer o número de personagens/fluxos, cada tela permanece isolada e fácil de localizar.

### `app/lib/widgets/`
**Função:** peças visuais reaproveitáveis em mais de uma tela.
**Entra:** bolha de chat, avatar circular, cartão de personagem, botões padronizados.
**Não entra:** nada que dependa de uma tela específica só ela usa — isso deveria estar dentro da própria pasta da tela.
**Relação:** usada por `screens/`; não deve depender de `screens/`.
**Motivo:** evita duplicar visual quando novos personagens/telas forem adicionados.

### `app/lib/services/`
**Função:** ponte entre o app e o backend.
**Entra:** funções que fazem requisições HTTP/WebSocket, tratam resposta, tratam erro de rede.
**Não entra:** lógica de IA, regras de negócio (isso é responsabilidade do backend).
**Relação:** chamada por `screens/`; consome `models/` para tipar os dados.
**Motivo:** se amanhã trocar a forma de comunicação (ex: REST → WebSocket para chat em tempo real), só essa camada muda.

### `app/lib/models/`
**Função:** representar os dados que circulam no app (o "formato" de um personagem, uma mensagem, um usuário).
**Entra:** classes de dados e conversão de/para JSON.
**Não entra:** lógica de tela ou chamada de rede.
**Relação:** usada por `services/`, `widgets/` e `screens/`.

### `app/lib/platform/`
**Função:** isolar as poucas diferenças reais entre mobile e web/desktop (ex: notificações push só existem em mobile).
**Motivo:** mantém o resto do código 100% compartilhado; só aqui existe ramificação por plataforma (ver seção 11).

---

### `backend/src/routes/`
**Função:** definir *quais* endpoints existem e para qual serviço encaminhar a chamada. Deve ser "fino" — sem regra de negócio.
**Não entra:** lógica de IA, cálculo de memória, validação complexa.
**Relação:** chama `services/`; é o ponto de entrada do backend.

### `backend/src/services/`
**Função:** onde a lógica de negócio realmente acontece.
**Subpastas e responsabilidade:**
- `auth/`: cadastro, login, sessão.
- `chat/`: orquestra o envio/recebimento de mensagens, decide se é conversa individual ou em grupo, monta o contexto que será enviado à IA.
- `character/`: CRUD de personagens, personas e avatares; regras de qual persona pode usar qual avatar.
- `memory/`: lê e grava as diferentes camadas de memória (seção 7), decide o que entra no contexto de uma conversa.
- `ai-gateway/`: única camada que efetivamente conversa com provedores de IA externos (seção 6).
**Motivo:** se uma regra de negócio muda, o ponto de alteração é sempre aqui — nunca em `routes/` nem no app.

### `backend/src/models/`
**Função:** representar as tabelas do banco via ORM.
**Não entra:** lógica de negócio (fica em `services/`).

### `backend/src/config/`
**Função:** variáveis de ambiente, chaves de API, parâmetros que mudam entre desenvolvimento e produção.
**Motivo:** nenhuma chave sensível deve estar espalhada pelo código.

### `backend/database/`
**Função:** controle de versão do schema (migrations) e dados de exemplo (seeds).

### `docs/`
**Função:** cada arquivo é a **fonte oficial** de um assunto — não deve haver dois documentos falando da mesma coisa. `decisions-log.md` registra o que foi **Definido / Em teste / Descartado**, evitando redecidir a mesma coisa depois.

## 4 e 5. Personagens: separação entre avatar e persona

O sistema não deve tratar "personagem" como uma pasta ou arquivo fixo (ex: `marco/`). Em vez disso, existem **duas entidades separadas no banco de dados**, ligadas entre si:

```
Avatar                         Persona (Personagem)
─────────────────              ──────────────────────
- aparência/imagem             - nome
- (futuro: voz, vídeo)         - personalidade
- id                            - forma de falar
                                 - história/backstory
                                 - regras de comportamento
                                 - avatar_id (referência)
                                 - relacionamento com o usuário
```

Uma **Persona** referencia um **Avatar**, mas não é o mesmo registro. Isso permite:
- o mesmo avatar visual ser reaproveitado por mais de uma persona (ex: mesmo rosto, personalidades diferentes em contextos diferentes);
- trocar a personalidade de um personagem sem mexer na parte visual, e vice-versa;
- no futuro, suportar personagens masculinos, femininos, casais, grupos — cada um é apenas um novo registro de Persona, não uma nova pasta ou novo código.

Essa separação vive em `backend/src/services/character/` e nas tabelas `character.model.js` / `avatar.model.js`.

---

## 6. Sistema de IA (camada de abstração)

Toda comunicação com modelos de IA passa exclusivamente por `backend/src/services/ai-gateway/`. Nenhuma outra parte do sistema (nem o app, nem as rotas, nem `chat/`) fala diretamente com um provedor de IA.

Estrutura interna sugerida:

```
ai-gateway/
├── conversation/        # interface única para "gerar resposta de texto"
├── vision/               # interface única para "analisar imagem"
├── image-generation/     # interface única para "gerar imagem"
├── video-generation/     # interface única para "gerar vídeo"
├── voice/                # interface única para "texto→voz / voz→texto"
└── index.js               # ponto único de entrada, decide qual provedor usar por função
```

Cada subpasta define **uma interface fixa** (ex: `gerarResposta(contexto) → texto`), e por trás dela pode existir qualquer provedor específico, plugado ou trocado sem que `chat/`, `character/` ou o app percebam diferença. Essa é a camada que garante o requisito "trocar modelos depois sem reconstruir o app".

---

## 7. Memória e contexto

Camadas separadas, todas geridas por `backend/src/services/memory/`:

| Camada | O que guarda | Escopo |
|---|---|---|
| Histórico de conversa | mensagens trocadas | por conversa |
| Contexto atual | recorte recente enviado à IA a cada chamada | por conversa, temporário |
| Memória do personagem | traços fixos daquela persona (não muda por usuário) | por persona |
| Memória do usuário | preferências, fatos que o usuário compartilhou | por usuário |
| Relacionamento usuário↔personagem | histórico específico daquele vínculo (nível, marcos, tom) | por par usuário+persona |
| Memória de grupo *(futuro)* | o que aconteceu numa conversa com múltiplos personagens | por conversa em grupo |

Tecnicamente, isso se traduz em tabelas separadas no banco (não um único "campo memória"), permitindo consultar só o necessário para montar o contexto de cada chamada de IA — evitando enviar memória irrelevante e mantendo custo/latência controlados.

---

## 8. Conversas individuais e em grupo

`backend/src/services/chat/` é responsável por decidir o tipo de conversa e montar o contexto adequado:

- **Individual:** contexto = histórico da conversa + memória daquela persona + memória do usuário + relacionamento.
- **Grupo:** o serviço de chat, a cada mensagem, monta o contexto **por personagem** (cada persona "vê" a conversa toda, mas responde com sua própria personalidade), e decide a ordem/quem responde. Isso exige que `conversation.model.js` suporte múltiplos participantes (não um campo fixo "personagem_id", mas uma tabela de participantes).

Nada disso é implementado agora — apenas a divisão em `chat/` (orquestração) e `memory/` (dados) já comporta essa evolução sem redesenho.

| Responsabilidade | Onde fica |

| Autenticação | `services/auth/` |
| Usuários | `services/` (auth) + `models/user.model.js` |

## 4. Estrutura dos personagens (o núcleo do sistema)

Em vez de um arquivo por personagem, existem **três entidades genéricas e reutilizáveis**, cada uma responsável por uma parte:

```
Character (character.model.js)      → entidade "guarda-chuva": liga persona + avatar + dono (usuário/sistema)
   ├── Persona (persona.model.js)   → nome, personalidade, forma de falar, história, regras
   ├── Avatar (avatar.model.js)     → aparência, imagem, futuramente voz/vídeo
   └── (config de IA por personagem, se precisar sobrescrever o padrão)
```

Cada nova "persona" (masculina, feminina, casal como duas personas ligadas à mesma conversa, etc.) é **um novo registro no banco**, nunca um novo arquivo de código. Os arquivos (`character.service.js`, `persona.service.js`, `avatar.service.js`) são genéricos e atendem qualquer quantidade de personagens.

Ficha de referência de cada persona (para uso da equipe, não do sistema em runtime) fica em `docs/characters/`, um arquivo markdown por personagem quando existirem.

## 5. Conversas individuais e em grupo

| Responsabilidade | Arquivo |
|---|---|
| Participantes de uma conversa (1 ou vários personagens) | `participant.model.js` — tabela que liga `conversation` a um ou mais `character` |
| Mensagens | `message.model.js` — cada mensagem referencia quem enviou (usuário ou qual personagem) |
| Contexto enviado à IA | montado dinamicamente por `individual_chat.service.js` ou `group_chat.service.js`, não fica salvo como arquivo fixo |
| Ordem das respostas em grupo | `group_chat.service.js` |
| Identificação de quem falou | campo `sender_id` + `sender_type` (usuário/personagem) em `message.model.js`; exibido no app via `speaker_tag.dart` |
| Relacionamento entre personagens (futuro) | ficaria em `relationship.model.js`, generalizado para também representar personagem↔personagem, não só usuário↔personagem |
| Memória da conversa em grupo | `conversation_memory.service.js` já é genérico o suficiente (não distingue individual/grupo na camada de dados) |

## 2. Relacionamentos entre User, Character, Persona e Avatar

```
User (1) ───< (N) Character
Persona (1) ───< (N) Character        [uma persona pode ser usada em vários Character,
                                        de usuários diferentes, se owner_type = system]
Avatar (1) ───< (N) Character         [mesma lógica — reaproveitamento]
Avatar (1) ───< (N) Persona           [via default_avatar_id]
```

- `Character` é sempre de 1 usuário (`user_id` obrigatório).
- `Persona` e `Avatar` podem pertencer ao sistema (`owner_type = system`, ex: personagens padrão oferecidos a todos) ou a um usuário específico (`owner_type = user`, ex: personagem customizado do zero).
- A separação persona/avatar permanece mesmo dentro de um `Character`: trocar o avatar de um personagem não cria uma nova persona, e vice-versa.

---

## 3. Conversa, Participantes e Mensagens

```
Conversation (1) ───< (N) Participant >─── (N) Character
Conversation (1) ───< (N) Message
Message.sender_id → User.id  OU  Character.id  (conforme sender_type)
```

- Conversa individual: 1 `Conversation` + 1 `Participant`.
- Conversa em grupo: 1 `Conversation` + N `Participant` (N ≥ 2).
- `Message.sender_type` evita precisar de duas tabelas de mensagem (uma para usuário, outra para personagem) — mantém tudo em uma única tabela, ordenável por `created_at`.

## 4. Camadas de memória — resumo de uso

| Camada | Escopo | Quando é lida |
|---|---|---|
| `Message` (histórico bruto) | por conversa | montagem do contexto recente |
| `ConversationMemory` | por conversa | quando o histórico bruto fica longo demais para caber no contexto de IA |
| `CharacterMemory` | por persona | sempre, para manter consistência da persona entre usuários diferentes |
| `UserMemory` | por usuário | sempre, para personalizar resposta ao usuário específico |
| `Relationship` | por par (user, character) | para ajustar tom conforme o nível do vínculo |
| `GroupMemory` *(futuro)* | por conversa em grupo | quando conversas em grupo forem implementadas |

A junção dessas camadas para montar o "contexto final" enviado à IA é responsabilidade do `ai-gateway` + `chat/` (Etapa 1/2), não do banco.

---

## 5. Relacionamento Usuário ↔ Personagem

Já coberto pela entidade `Relationship` (seção 1.9). Pontos de integridade:
- Um par (`user_id`, `character_id`) deve ser único — não existe mais de um registro de relacionamento para o mesmo par.
- `level` e `milestones` são opcionais porque a decisão de gamificar ou não o vínculo ainda não foi tomada — **a definir**.

---

## 6. Preparação para conversas em grupo

Já modelado via `Participant` (N para N entre `Conversation` e `Character`) e `Message.sender_type/sender_id`. Pontos que ficam **a definir** antes da implementação real:
- Regra de quem responde e em que ordem (lógica de serviço, não de dados).
- Se personagens podem ser adicionados/removidos de uma conversa em grupo já existente (exigiria `left_at` em `Participant` — campo ainda não incluído, marcado como futuro).

---

## 7. Assinatura/monetização — apenas preparação

Coberto pela entidade `Subscription` (seção 1.10). Nenhum plano, preço, gateway de pagamento ou regra de cobrança é definido aqui. A entidade existe só para o schema já prever o relacionamento `User (1) ─── (0..1 ativo) Subscription`.

## 8. Relações entre entidades e regras de integridade

```
User 1 ──< N Character
User 1 ──< N Conversation
User 1 ──< N UserMemory
User 1 ──< 0..1 Subscription (ativa)

Persona 1 ──< N Character
Persona 1 ──< N CharacterMemory
Avatar 1 ──< N Character
Avatar 1 ──< N Persona (via default_avatar_id)

Conversation 1 ──< N Participant
Conversation 1 ──< N Message
Conversation 1 ──< 0..1 ConversationMemory
Conversation 1 ──< 0..1 GroupMemory (futuro, só se type = group)

Character 1 ──< N Participant
Character 1 ──< N Relationship
```

**Regras de integridade principais:**
1. `Character.user_id`, `persona_id`, `avatar_id` são obrigatórios — um Character nunca existe sem os três.
2. `Message.sender_id` deve corresponder a uma entidade válida conforme `sender_type` (validação em nível de aplicação, já que é chave estrangeira "polimórfica" — bancos relacionais não validam isso nativamente).
3. `Participant` não permite duplicar o mesmo `character_id` na mesma `Conversation`.
4. `Relationship` é única por par (`user_id`, `character_id`) quando `subject_type = user_character`.
5. Exclusão de `User`: **a definir** se será exclusão física (apaga tudo em cascata) ou lógica (`status = deleted`, mantendo dados por período de retenção) — decisão pendente de política de privacidade.

# DOCUMENTO DE INTEGRAÇÃO DAS ETAPAS 1–4 — CHATBOT NAMORADO VIRTUAL

As Etapas 1, 2, 3 e 4 continuam sendo os documentos oficiais e independentes do projeto. Este documento não substitui, resume nem altera nenhuma delas — apenas mostra como se conectam.

---

## 1. Função de cada etapa

- **Etapa 1 — Arquitetura:** define os princípios (avatar separado de persona, IA em camada trocável, memória em camadas, individual/grupo) e a divisão macro de responsabilidades.
- **Etapa 2 — Esqueleto de pastas e arquivos:** materializa a Etapa 1 em pastas, arquivos e responsabilidades concretas, sem implementação.
- **Etapa 3 — Dados e entidades:** define os campos, tabelas e relacionamentos que os arquivos da Etapa 2 vão manipular.
- **Etapa 4 — Plano de implementação:** define a ordem em que tudo isso deve ser construído.

---

## 2. Como uma etapa alimenta a seguinte

**Etapa 1 → Etapa 2**
Cada princípio da arquitetura virou uma pasta/arquivo específico: a separação persona/avatar gerou `persona.service.js` e `avatar.service.js` separados; o `ai-gateway` da Etapa 1 virou a pasta `ai-gateway/` com uma subpasta por função (conversação, visão, imagem, vídeo, voz).

**Etapa 2 → Etapa 3**
Os arquivos e serviços da Etapa 2 (`character.service.js`, `chat.service.js`, `memory/*.service.js`) foram o ponto de partida para decidir quais entidades e campos a Etapa 3 precisava definir — cada serviço da Etapa 2 tem uma ou mais entidades correspondentes na Etapa 3.

**Etapa 3 → Etapa 4**
As dependências entre entidades (`Character` depende de `Persona`+`Avatar`; `Message` depende de `Conversation`+`Participant`) determinaram diretamente a ordem das migrations e das fases de backend na Etapa 4.

**Etapa 1 → Etapa 4**
A Etapa 4 não implementa nada fora da arquitetura da Etapa 1 — por isso o `ai-gateway` entra como camada isolada (Fase 5) mesmo antes de haver um provedor definitivo, e grupo/mídia/assinatura ficam explicitamente fora do escopo do protótipo, exatamente como a Etapa 1 já os tratava como extensões futuras.

---

## 3. Fluxos principais de integração

**Criação de personagem:**
```
Tela (character_creation_screen.dart)
  → character_api.dart
    → character.routes.js
      → character.service.js (+ persona.service.js, avatar.service.js)
        → entidades Character / Persona / Avatar
          → banco (PostgreSQL)
```

**Conversa individual:**
```
Tela (individual_chat_screen.dart)
  → chat_api.dart
    → chat.routes.js
      → individual_chat.service.js
        → memory/*.service.js (monta contexto: ConversationMemory + CharacterMemory + UserMemory + Relationship)
          → ai-gateway/conversation
            → resposta
              → gravada como Message
                → retorna ao frontend
```

---

## 4. Dependências

```
Banco (Etapa 3) → Backend: auth/user → Backend: personagem (persona/avatar/character)
   → Backend: conversa individual → ai-gateway (mínimo) → memória
      → Frontend: onboarding/auth → Frontend: criação de personagem → Frontend: chat
```

Nenhuma dependência nova é criada aqui — esta é a mesma cadeia já descrita na Etapa 4, seções 1–3.

---

## 5. Regra de acoplamento

- Telas do Flutter **nunca** acessam o backend diretamente — sempre passam por `services/api/`.
- `routes/` do backend apenas encaminha para `services/`; não contém regra de negócio.
- `services/` aplica as regras e é o único ponto que acessa `models/` e o `ai-gateway`.
- O chat **sempre** passa pelo `ai-gateway` — nenhum outro módulo fala diretamente com um provedor de IA.
- A memória participa da montagem do contexto **antes** de qualquer chamada ao `ai-gateway`, nunca depois.
- O banco de dados fica isolado atrás de `models/`; nenhuma tela ou rota consulta o banco diretamente.

---

## 6. Ordem de construção (referência à Etapa 4, sem nova ordem)

```
Estrutura vazia → Banco → Auth/Usuário → Personagem → Chat individual (simulado)
→ ai-gateway (mínimo) → Memória → Frontend (onboarding → personagem → chat)
→ Protótipo funcional individual
→ (preparado, não implementado): grupo, mídia, assinatura
```

Cada fase da Etapa 4 só pode começar quando a fase anterior desta sequência estiver pronta — isso já estava definido na Etapa 4 e é apenas reafirmado aqui como mapa de consulta.
